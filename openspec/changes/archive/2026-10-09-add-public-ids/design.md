## Context

- Наружу сейчас выходят: `id` в `PhotoSerializer`, `GallerySerializer`, `CategorySerializer`, `MeSerializer` (`str(pk)`); `pk` в путях `galleries/<int:pk>`, `me/favorites/<int:photo_id>`; `sub` в JWT (`AccessTokenService`), `uid` в `EmailTokenService` (payload `signing` читается без ключа).
- Пользователь — стандартный `auth.User`, своих полей добавить нельзя.
- В базе compose уже есть данные (9 галерей, фото, пользователи) — нужна миграция с заполнением.

## Goals / Non-Goals

**Goals:** реализовать `public-ids`; поиск по публичному id одним индексированным запросом; один механизм для всех сущностей.

**Non-Goals:** скрытие id в URL админки; ротация всех id при смене `SECRET_KEY`; история старых идентификаторов.

## Decisions

### Формат и вычисление
`public_id = base32(HMAC-SHA256(key, f"{model_label}:{pk}:{link_date.isoformat()}")[:16]).lower().rstrip('=')` — 26 символов `[a-z2-7]`, 128 бит.
- Ключ — `salted_hmac` с солью `public-id` поверх `SECRET_KEY` (отдельная соль: значение нельзя использовать как подпись в других местах).
- `model_label` в данных хеша — у разных моделей с одинаковым pk и датой разные id.
- base32 в нижнем регистре: только буквы и цифры, безопасно в URL, не зависит от регистра.
- *Альтернатива:* Hashids/Sqids — обратимое кодирование числа, «соль» не секрет в криптографическом смысле, и нет встроенной даты/отзыва. Отклонено.
- *Альтернатива:* случайный UUID — не «хеш с вшитой датой», перевыпуск = просто новое случайное значение. Функционально тоже подошло бы, но владелец явно просил хеш от даты.

### Хранение
Публичный id **хранится** в колонке `public_id` (`CharField(26, unique)`), пересчитывается при сохранении, если изменилась `link_date` (или пуст). Колонки `public_id` и `link_date` в БД допускают NULL: хешу нужен pk, который появляется после вставки, поэтому `save()` вставляет строку и сразу дописывает оба поля. Через модель они всегда заполнены; уникальность в PostgreSQL допускает несколько NULL. Поиск — `get(public_id=...)`, индексированный.
- Хранение, а не вычисление на лету: обратного преобразования нет, а пересчёт для поиска потребовал бы перебора.
- Смена `SECRET_KEY` не меняет уже выданные id (они пересчитываются только при смене даты ссылки) — ссылки не ломаются при ротации ключа.

### Общий механизм
- Абстрактная модель `core`-уровня `PublicIdModel` с полями `link_date` (`DateTimeField`) и `public_id` и логикой в `save()`: если `link_date` пуста — взять дату создания (`created_at`), посчитать `public_id`. Нужен pk, поэтому для новой записи — сохранить, затем посчитать id и обновить одно поле (`update_fields`).
- Абстрактная модель и функция хеша — в новом небольшом приложении-библиотеке `common` без своих таблиц: механизм общий для `gallery` и `accounts`, и ни одно из них не должно зависеть от другого ради него. `Gallery`, `Photo`, `Category` наследуют `PublicIdModel`.
- Пользователь: `accounts.Profile(user OneToOne, link_date, public_id)` на той же абстракции, `created_at` берётся из `user.date_joined`. Профиль создаётся сигналом `post_save` у `User` и миграцией для существующих пользователей.

### Перевыпуск
- Формы админки с полем даты (`LinkDateFormMixin`): виджет даты-времени отбрасывает микросекунды, поэтому сохранение формы без правки даты записало бы немного другую дату и молча перевыпустило id. Если поле не менялось (`changed_data`), сохраняется прежнее точное значение.
- Админка: поле `link_date` в формах галереи, категории и профиля (inline у пользователя); действие «Перевыпустить ссылку» в списках галерей, категорий, пользователей — ставит `link_date = now()` и сохраняет.
- Фото: в блоке «С выбранными» сетки галереи — флажок «перевыпустить ссылки» (рядом с «перенести»/«удалить»), выполняется в `PhotoService.reissue_links(photos)`.
- Избранное, обложка, файлы ссылаются на внутренний pk — перевыпуск их не затрагивает.

### Токены
- `AccessTokenService`: `sub = profile.public_id`; `verify` возвращает публичный id; аутентификация ищет `User` по `profile__public_id` (`select_related('profile')`, индекс уникальный). Перевыпуск ссылки пользователя → старые access не находят пользователя → 401.
- `EmailTokenService`: `uid` = публичный id; поиск по нему. Публичный id не входит в «отпечаток состояния», но смена его и так делает старый токен ненаходимым.
- Refresh-токены непрозрачные и не содержат id — без изменений.

### Миграции
`gallery.0009_public_ids`: `AddField link_date`, `public_id` (nullable, unique) → `RunPython` (link_date = created_at, public_id по формуле; алгоритм продублирован в миграции, чтобы не зависеть от будущих изменений кода, тест сверяет копию с кодом). `accounts.0002_profile`: модель `Profile` + `RunPython`, создающий профиль каждому существующему пользователю (link_date = date_joined).

## Risks / Trade-offs

- [Фронт где-то полагается на числовой вид id (сортировка, `Number(id)`)] → в сводке для фронта явно сказать, что `id` — непрозрачная строка.
- [Перевыпуск ссылки пользователя разлогинивает его на ≤15 минут до refresh] → ожидаемо, это и есть отзыв.
- [Утечка `SECRET_KEY` позволяет вычислить id по известным pk и датам] → те же последствия, что и без этой фичи (ключом подписаны JWT и письма); ротация ключа + перевыпуск дат.
- [Дублирование алгоритма в миграции] → тест сверяет id, посчитанный кодом, с результатом миграции на тестовой записи.

## Migration Plan

1. Применить миграции (контейнер `app` при старте); существующие записи получат id.
2. Сообщить фронту: старые ссылки `/galleries/<число>` станут 404.
3. Откат: обратные миграции удаляют поля; API вернётся к числовым id только вместе со старым кодом.
