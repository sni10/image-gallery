## Context

- Бэкенд: Django 6.1 + DRF, Python 3.14, PostgreSQL, запуск через Docker Compose (nginx → gunicorn). Фронт — отдельное SPA (`image-gallery-front`) на другом origin, ходит в API через CORS.
- Настройки читаются из env через `config/app_settings` (pydantic-settings) с валидацией; новые настройки должны идти тем же путём.
- Сейчас аутентификация DRF выключена (`DEFAULT_AUTHENTICATION_CLASSES = []`), API полностью публичное. Админка работает на сессиях Django.
- Пользователи — стандартная модель `django.contrib.auth.models.User`, в базе уже есть суперпользователь и залитые галереи.
- Код разложен по слоям: `services/` (логика), `api/` (сериалайзеры, вьюхи, пагинация), `admin/`. Новое пишется так же.
- Почта: в Django 6.1 настройка `MAILERS`, сейчас `default` — консольный бэкенд.

## Goals / Non-Goals

**Goals:**
- Реализовать `user-auth`, `user-profile`, `favorites` из specs без изменения существующих контрактов галереи, кроме нового поля `isFavorite`.
- Не трогать админку и её вход.
- Держать логику в сервисах, чтобы вьюхи оставались тонкими и тестируемыми.

**Non-Goals:**
- Своя модель пользователя (`AUTH_USER_MODEL`), очереди для отправки писем, восстановление пароля, соцсети.

## Decisions

### Модель пользователя: стандартный `User`, `username = email`
Email (в нижнем регистре) пишем и в `username`, и в `email`. Уникальность email обеспечивает существующий unique-индекс на `username`; вход — по `username`.
- *Альтернатива:* своя модель с `USERNAME_FIELD = 'email'`. Правильнее для нового проекта, но смена `AUTH_USER_MODEL` на живой базе с данными требует ручной миграции таблиц `auth`/`admin`. Выигрыш не стоит риска.
- Аккаунт до подтверждения: `is_active = False`. Стандартная проверка Django уже не пускает неактивных; отдельный флаг не нужен.

### Токены доступа: access — JWT на PyJWT, refresh — непрозрачный токен в БД
**Access-токен** — JWT HS256, подписывается и проверяется `PyJWT`. Claims: `sub` (id пользователя строкой), `type: "access"`, `iat`, `exp` (+15 мин). Ключ — `SECRET_KEY`, отдельный не заводим. При проверке алгоритм жёстко `HS256` (`algorithms=["HS256"]`), `exp` обязателен, `type` должен быть `access`. Access нигде не хранится и не отзывается — живёт до `exp`.

**Refresh-токен** — не JWT, а случайная строка `secrets.token_urlsafe(32)`. В БД хранится только её SHA-256: модель `accounts.RefreshToken(user, token_hash [unique], family, created_at, expires_at, revoked_at)`.
- Выдача (вход, подтверждение email, смена пароля): новая запись, новая `family` (UUID).
- Обмен (`/auth/refresh`): находим по хешу; если не найден или истёк → 401. Если уже отозван → это повторное использование (кража): отзываем все токены пользователя → 401. Иначе помечаем отозванным и выдаём новый в той же `family`. Обмен — в транзакции с `select_for_update`, чтобы два параллельных обмена одного токена не прошли оба.
- Выход: отзыв предъявленного токена. Смена пароля: отзыв всех токенов пользователя.
- Просроченные и отозванные записи периодически чистятся (команда `manage.py` либо удаление при выдаче — решается в реализации, на контракт не влияет).

**Аутентификация DRF** — свой класс (~25 строк): читает `Authorization: Bearer <access>`, проверяет JWT, загружает пользователя; если токен битый/просрочен или пользователь не найден/неактивен → `AuthenticationFailed` (401). Без заголовка → аноним. `DEFAULT_AUTHENTICATION_CLASSES` = этот класс, `DEFAULT_PERMISSION_CLASSES` остаётся `AllowAny`; закрытые вьюхи (`/me/...`) ставят `IsAuthenticated` явно.

Ответ входа, подтверждения и refresh — `{ "access", "refresh" }`.

- *Почему не `djangorestframework-simplejwt`:* последний релиз 21.07.2025, официальной поддержки Django 6 и Python 3.14 нет. Плюс его refresh — тоже JWT, и для отзыва нужен отдельный blacklist; хранение refresh в БД даёт честный отзыв и обнаружение повторного использования проще.
- *Почему не всё в JWT (refresh тоже):* stateless refresh нельзя отозвать без той же таблицы — выигрыша нет.
- *Почему не opaque access-токены в БД (DRF TokenAuthentication / Knox):* запрос к БД на каждый вызов API и без срока жизни по умолчанию; выбор JWT зафиксирован при постановке задачи.

### Токены в письмах: подписанные одноразовые токены без таблицы
Для подтверждения регистрации и смены email — токены на основе `django.contrib.auth.tokens.PasswordResetTokenGenerator` (своими подклассами с разной солью). Генератор хеширует состояние пользователя, поэтому токен сам становится недействительным после события:
- подтверждение регистрации: в хеш входит `is_active` → после активации токен мёртв;
- смена email: в хеш входят текущий email и новый email; новый email передаётся в токене подписанным через `django.core.signing` вместе с id пользователя → после смены email токен мёртв, подмена адреса невозможна.
Срок жизни 24 часа (`PASSWORD_RESET_TIMEOUT` не трогаем — у подклассов свой таймаут).
- *Альтернатива:* таблица токенов в БД. Не нужна: одноразовость и срок дают подпись и хеш состояния.

### Ссылки в письмах ведут на фронт
`FRONTEND_URL` из env (секция настроек `FRONTEND_`). Письмо содержит `<FRONTEND_URL>/confirm-email?token=...` и `<FRONTEND_URL>/confirm-email-change?token=...`; фронт отправляет токен в API. Так API остаётся JSON-only, а страницу показывает SPA.

### Почта: `MAILERS['default']` из env
Новая секция `EMAIL_` в `config/app_settings`: бэкенд (`console`/`smtp`), host, port, user, password (`SecretStr`), TLS, адрес отправителя. В разработке — консоль, в compose/проде — SMTP. Письма отправляются синхронно внутри запроса и текстом (без HTML).

### Структура кода
- Новое приложение `accounts`: модель `RefreshToken`; `services/` (регистрация, подтверждение, смена email/пароля, отправка писем, токены писем, выдача/ротация/отзыв JWT-пары); `authentication.py` (класс аутентификации DRF); `api/` (сериалайзеры, вьюхи, urls `/auth/...` и `/me`, `/me/email`, `/me/password`).
- Избранное — в приложении `gallery` (это связь пользователя с фото): модель `Favorite(user, photo, created_at)` с уникальностью пары и индексом `(user, -created_at)`; удаление фото или пользователя каскадом удаляет запись. Эндпоинты `/me/favorites...` живут в `gallery/api`.
- `isFavorite`: в queryset фото добавляется аннотация `Exists(Favorite для request.user)` (для анонима — константа `False`), сериалайзер читает её. Один подзапрос на список, без N+1. Обложки галерей (`attach_covers`) получают ту же аннотацию.

### Ограничение частоты
DRF `ScopedRateThrottle`, scope на каждый эндпоинт, `10/min`, ключ — IP. Кеш — стандартный `LocMemCache`.

## Risks / Trade-offs

- [Собственная обвязка вокруг токенов — место для ошибок безопасности] → криптографию (подпись, проверка, `exp`) делает PyJWT; наш код только выдаёт и хранит токены. Обязательные тесты: просроченный access, подделанная подпись, `alg: none`, refresh в роли access (`type`), неактивный пользователь, повторное использование refresh, параллельный обмен одного refresh.
- [Утечка БД не должна давать рабочие refresh-токены] → в БД только SHA-256 токена.
- [`LocMemCache` у каждого воркера gunicorn свой → фактический лимит 10 × число воркеров] → приемлемо на старте; при необходимости — Redis-кеш, specs не меняются.
- [Синхронная отправка писем: медленный SMTP задерживает ответ регистрации, падение SMTP даёт 500] → таймаут SMTP-соединения в настройках; если станет проблемой — очередь (Celery/RQ).
- [Refresh-токен хранится на фронте; при XSS его можно украсть] → короткий access, ротация refresh, отзыв всех refresh при смене пароля. Рекомендация фронту: access держать в памяти, refresh — в `localStorage` (или перейти на httpOnly-cookie отдельным изменением).
- [Битый токен на публичном эндпоинте даёт 401] → описано в specs; фронт при 401 обновляет токен, при неудаче — выходит и повторяет запрос анонимно.
- [`username = email`: при смене email меняется и `username`] → суперпользователь админки со старым `username` (не email) продолжает входить в админку; через API он не логинится — для него это не нужно.

## Migration Plan

1. Миграции: `accounts.RefreshToken`, `gallery.Favorite`. Данные существующих таблиц не меняются.
2. Новые переменные `.env`/`.env.example`: `FRONTEND_URL`, `EMAIL_*`; в compose — SMTP-параметры (для локального compose можно оставить консоль).
3. Откат: выключить новые URL и вернуть `DEFAULT_AUTHENTICATION_CLASSES = []`; таблицы можно оставить — публичное API от них не зависит.
