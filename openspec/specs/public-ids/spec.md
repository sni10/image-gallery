# public-ids Specification

## Purpose
Скрыть внутренние id базы данных: наружу (API, ссылки, токены) выдаются только непрозрачные публичные идентификаторы, которые администратор может перевыпустить, чтобы отозвать распространившуюся ссылку.

## Requirements

### Requirement: Только публичные идентификаторы в API
Поле `id` галереи, фото, категории и пользователя во всех ответах API SHALL быть публичным идентификатором: строкой из 26 символов `[a-z2-7]`. Внутренние id базы данных MUST NOT появляться ни в одном ответе API. По публичному идентификатору MUST быть невозможно определить внутренний id, число записей или порядок их создания.

#### Scenario: Галерея в каталоге
- **WHEN** запрашивается `GET /galleries`
- **THEN** у каждой галереи, её категории и фото-обложки `id` — строка из 26 символов `[a-z2-7]`, а не число

#### Scenario: Соседние записи
- **WHEN** созданы две галереи подряд
- **THEN** их публичные идентификаторы не связаны между собой: по одному нельзя получить другой

### Requirement: Пути принимают только публичные идентификаторы
`GET /galleries/{id}`, `GET /galleries/{id}/photos`, `PUT /me/favorites/{photoId}` и `DELETE /me/favorites/{photoId}` SHALL находить запись по публичному идентификатору. Внутренний числовой id или неизвестный идентификатор MUST давать `404` (для `DELETE /me/favorites` — `204` без изменений, как для отсутствующей записи).

#### Scenario: Открытие галереи
- **WHEN** запрос `GET /galleries/<публичный id галереи>`
- **THEN** ответ `200` с этой галереей

#### Scenario: Числовой id
- **WHEN** запрос `GET /galleries/8`, где 8 — внутренний id существующей галереи
- **THEN** ответ `404`

### Requirement: Дата ссылки
Каждая галерея, фото, категория и пользователь SHALL иметь «дату ссылки» — отдельную от даты создания дату-время. При создании записи она MUST быть равна дате создания; для записей, существовавших до обновления, — их дате создания. Публичный идентификатор MUST вычисляться из внутреннего id, даты ссылки и секрета сервера и MUST оставаться неизменным, пока не меняется дата ссылки.

#### Scenario: Новая запись
- **WHEN** администратор создаёт галерею
- **THEN** её дата ссылки равна дате создания, у неё есть публичный идентификатор

#### Scenario: Стабильность
- **WHEN** у галереи меняют название или категорию, но не дату ссылки
- **THEN** публичный идентификатор не меняется

### Requirement: Перевыпуск ссылки
Смена даты ссылки SHALL сразу менять публичный идентификатор записи. Старый идентификатор MUST перестать работать: запросы с ним дают `404`, редиректа на новый нет. Дата создания записи MUST при этом не меняться. Админка SHALL позволять менять дату ссылки галереи, категории и пользователя и перевыпускать её (поставить текущее время) одним действием; для фото — действием над выбранными фото в сетке галереи.

#### Scenario: Отзыв ссылки на галерею
- **WHEN** администратор перевыпускает ссылку галереи, у которой был публичный id `A`
- **THEN** у галереи новый публичный id `B`, `GET /galleries/A` даёт `404`, `GET /galleries/B` даёт `200`

#### Scenario: Перевыпуск фото
- **WHEN** администратор отмечает фото в сетке галереи и выбирает «перевыпустить ссылки»
- **THEN** у этих фото новые публичные id, у остальных — прежние; избранное пользователей сохраняется

### Requirement: Токены без внутренних id
Access-токен (claim `sub`) и токены в ссылках из писем SHALL идентифицировать пользователя только публичным идентификатором. Смена даты ссылки пользователя MUST делать недействительными его ранее выданные access-токены и неиспользованные ссылки из писем.

#### Scenario: Содержимое access-токена
- **WHEN** клиент декодирует свой access-токен (без проверки подписи)
- **THEN** `sub` равен `id` из `GET /me`, а не внутреннему id

#### Scenario: Перевыпуск ссылки пользователя
- **WHEN** администратор перевыпускает ссылку пользователя
- **THEN** его прежний access-токен даёт `401`, а `GET /me` с новым токеном (после `POST /auth/refresh`) возвращает новый `id`
