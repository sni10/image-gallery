# ТЗ: API не отдаёт гостям ссылки на закрытые оригиналы

## Зачем

Весь контент сайта NSFW. Гость (запрос без токена) должен видеть оригиналы только у первых 10 фото каждой галереи.
Для остальных фото гость получает только превью; по клику фронт предлагает войти.

Сейчас фронт закрывает фото только блюром, а `url` оригинала всё равно приходит в API и HTML. Любой, кто откроет
DevTools, может посмотреть фото напрямую. После этой задачи ссылки на закрытые оригиналы гостю не приходят вообще.

## Правило

Фото **закрыто** для запроса, если выполнены оба условия:
1. запрос анонимный (`request.user.is_anonymous`);
2. фото **не входит в первые `GUEST_FREE_PHOTOS` = 10 фото своей галереи**. Порядок тот же, что в
   `GET /galleries/{id}/photos`, сейчас `-id`, то есть сначала новые.

### Главная (`GET /photos?seed=…`): первые 10 позиций ленты открыты, остальные закрыты

Гость видит открытыми первые `GUEST_FREE_PHOTOS` = 10 позиций ленты (позиции 1–10 по всей ленте, а не по
странице), остальные фото закрыты.

**Открытыми на главной могут быть только фото, которые и так открыты в своих галереях** (первые 10 галереи).
Нельзя просто открыть первые 10 случайных фото: `seed` выбирает клиент. Перебирая `seed=a`, `seed=b`, … гость
получит по 10 новых оригиналов за запрос и скачает весь сайт, то есть защита теряет смысл.

Как сделать: для гостя сортировать ленту так, чтобы сначала шли фото, открытые в своих галереях (в случайном
порядке по `seed`), затем остальные:

```python
PhotoQueries.shuffled(seed).annotate(guest_free=…).order_by('-guest_free', <текущая сортировка по seed>)
```

Затем открыть позиции 1–10, позиции 11+ закрыть, даже если фото входит в первые 10 своей галереи. Итог:
- гость видит на главной 10 открытых фото, и все они из тех, что уже открыты в галереях. Новых оригиналов
  гостю это не открывает;
- лента с одним `seed` стабильна между страницами, как сейчас;
- для пользователя с токеном сортировка и всё остальное без изменений.

Если в галереях вместе меньше 10 открытых фото, открытых на главной будет столько, сколько есть.

Пользователю с токеном всё открыто, как сейчас.

`GUEST_FREE_PHOTOS` вынести в settings, со значением по умолчанию 10.

## Что меняется в ответе фото

Это касается `PhotoSerializer` везде, где он используется: списки, `GET /photos/{id}`, `cover` в галереях.

| Поле | Открытое фото | Закрытое фото |
| --- | --- | --- |
| `locked` (новое, boolean) | `false` | `true` |
| `url` | ссылка на оригинал | **`null`** |
| `thumbUrl` | превью | превью (WebP ≤400px), как сейчас |
| `width`, `height`, `id`, `title`, `isFavorite` | как сейчас | как сейчас (размеры нужны фронту для раскладки сетки) |
| `description`, `tags` | как сейчас | как сейчас (нужны для SEO страницы фото) |

Важные детали:
- **`thumbUrl` не должен падать на оригинал.** Сейчас `get_thumb_url` возвращает `obj.thumb or obj.image`: если
  превью нет, это прямая утечка оригинала. Для закрытого фото без превью отдавать `thumbUrl: null`. Фронт покажет
  заглушку. Ещё лучше гарантировать, что превью есть у всех фото.
- `url` становится nullable. В OpenAPI нужно поменять схему (`allow_null`) и описать `locked`.
- Коды ответов не меняются: гость получает **200**, а не 401/403. Закрытость фото — это данные, а не ошибка доступа.

## Эндпоинты

| Эндпоинт | Что делать для гостя |
| --- | --- |
| `GET /galleries/{id}/photos` | первые 10 фото галереи открыты, остальные закрыты. Считать позицию **в галерее**, а не на странице: при `limit=20` на `page=2` все фото закрыты |
| `GET /photos?seed=…` | позиции 1–10 ленты открыты (только из фото, открытых в своих галереях), остальные закрыты; см. «Главная» выше |
| `GET /photos/{photo_id}` | открыто, если фото входит в первые 10 своей галереи, иначе закрыто |
| `GET /galleries`, `GET /galleries/{id}` → `cover` | то же правило, что для фото галереи. Каталог показывает `thumbUrl`, поэтому визуально ничего не меняется |
| `GET /me/favorites` | только с токеном, без изменений |
| `POST /ingest/photos` | без изменений (ключ, а не пользователь) |

### Как посчитать «первые 10 галереи» (подсказка, решать разработчику)

Одна аннотация, которая работает одинаково для списков, детали и обложек:

```python
newer = Photo.objects.filter(gallery=OuterRef('gallery'), id__gt=OuterRef('id'))
photos.annotate(guest_free=~Exists(newer[settings.GUEST_FREE_PHOTOS - 1:]))  # или Count-подзапрос < 10
```

Аннотацию добавить в `PhotoQueries`, рядом с `with_is_favorite`, только для анонимного пользователя. Сериализатор
читает `locked` из аннотации так же, как `is_favorite`. Оконная функция (`RowNumber`) не подходит:
в `GET /photos/{id}` выборка из одной строки, и номер всегда получится 1. Индекс `(gallery_id, id)` уже должен
быть через FK и PK. Проверить `EXPLAIN` на большой галерее.

## Кэш

Ответ теперь зависит от `Authorization`. Нужно отдавать `Vary: Authorization` и не кэшировать ответы API на прокси.
Проверить, что Cloudflare не кэширует JSON (по умолчанию не кэширует, но правило «Cache Everything» это сломает).

## Подписанные ссылки на оригиналы (входит в задачу)

Сейчас `/media/*` раздаётся Caddy публично, с `Cache-Control: public, max-age=31536000, immutable`. Скрыть `url`
в API недостаточно: ссылку на оригинал, которую получил залогиненный пользователь, может открыть кто угодно и
навсегда. Поэтому оригиналы отдаются **только по подписанной ссылке с ограниченным сроком жизни**.

### Что защищается

| Путь | Доступ |
| --- | --- |
| `/media/original/*` (поле `Photo.image`, это и есть `url`) | только с действующей подписью |
| `/media/thumb/*` (превью) | публично, как сейчас: превью видит и гость, его можно кэшировать навсегда |
| `ORIGINALS_ROOT` (чистые оригиналы, только для app) | без изменений, наружу не раздаётся |

### Формат ссылки

`url` в API становится таким: `https://api.artai.win/media/original/ab/cd/<sha256>.jpg?exp=<unix>&sig=<hmac>`

- `sig` — это HMAC-SHA256 от `path + exp`. Ключ — отдельный секрет `MEDIA_SIGNING_KEY` в `.env`, не `SECRET_KEY`:
  тогда его можно сменить, не разлогинив всех пользователей. В подписи сравнивать через `hmac.compare_digest`.
- **Срок** — `MEDIA_URL_TTL`, по умолчанию 6 часов. Страница с лайтбоксом может долго висеть открытой, поэтому
  срок не меньше нескольких часов.
- **`exp` округлять вверх до часа.** Тогда в течение часа ссылка на одно и то же фото не меняется, и браузерный кэш
  работает. Если генерировать новую подпись на каждый запрос, пользователь будет скачивать оригинал заново при каждом просмотре.
- Подпись выдаётся **только тем, кому фото открыто** по правилу выше: залогиненному — всегда, гостю — для первых
  10 фото галереи. Закрытое фото по-прежнему получает `url: null`.

### Проверка подписи: Caddy `forward_auth` → Django

```caddyfile
handle /media/original/* {
	forward_auth app:8000 {
		uri /internal/media-auth?{query}&path={path}
	}
	root * /srv
	header Cache-Control "private, max-age=3600"
	header X-Content-Type-Options nosniff
	file_server
}
```

- Django-вьюха `/internal/media-auth` проверяет `exp` (не истёк) и `sig`. Если всё верно, отвечает 204, если нет — 403.
  Запросов к БД нет, только HMAC, поэтому это быстро.
- `/internal/*` **не должен быть доступен снаружи**: Caddy отдаёт на него 404 для внешних запросов, как сейчас
  сделано с `/admin/` на `api.artai.win`.
- Ответ с оригиналом: `Cache-Control: private`. Кэшировать могут браузеры, общие кэши — нет.
- Cloudflare: для `/media/original/*` правило «Bypass cache». Иначе Cloudflare закэширует файл и будет отдавать
  его по этой ссылке до конца срока, не проверяя подпись. Превью (`/media/thumb/*`) кэшировать можно и нужно.
- Альтернатива на усмотрение разработчика: Django сам отдаёт файл (`FileResponse`). Это проще в конфиге, но
  нагружает gunicorn. `forward_auth` предпочтительнее.

### Что сломается и что проверить

- **Старые прямые ссылки на оригиналы перестанут работать.** Это ожидаемо, они и были дырой.
- `og:image`, sitemap и всё, что читают боты, должно ссылаться **только на превью**. Боты не логинятся, а
  подписанная ссылка истекает. Проверить `gallery/sitemaps.py`, если в нём есть картинки.
- Админка (`secure.artai.win`) показывает оригиналы: там тоже генерировать подписанные ссылки или отдавать через
  отдельный путь для staff.
- `POST /ingest/photos` возвращает фото: `url` там тоже подписанный (ключ ingest считается «открытым» доступом).

## Тесты

- Гость, галерея из 12 фото: в `GET /galleries/{id}/photos` первые 10 с `url` и `locked=false`, 11-е и 12-е с
  `url=null` и `locked=true`. С `limit=5`: `page=2` (позиции 6–10) вся открыта, на `page=3` (11–12) обе закрыты.
- Тот же запрос с токеном: все 12 открыты.
- `GET /photos?seed=…` гостем, две галереи по 12 фото:
  - первые 10 позиций ленты с `url`, и каждое из них входит в первые 10 своей галереи;
  - позиции 11+ с `url=null`;
  - `page=2` (при `limit=5`) продолжает ленту, без повторов и пропусков;
  - для разных `seed` множество открытых фото всегда из одних и тех же 20 «открытых в галереях», а не из всех 24.
- `GET /photos?seed=…` с токеном: все `url` заполнены, порядок как раньше.
- `GET /photos/{id}` гостем: для 3-го фото галереи `url` есть, для 11-го `url=null`.
- `cover` закрытого фото у гостя: `url=null`, `thumbUrl` есть.
- Закрытое фото без превью: `thumbUrl=null`, оригинал не утекает ни в одно поле.
- В OpenAPI `url` nullable, `locked` описан.
- Подпись:
  - `url` открытого фото содержит `exp` и `sig`; `/internal/media-auth` с ними отвечает 204;
  - изменённый `sig`, чужой `path` с этой подписью, истёкший `exp` дают 403;
  - без параметров — 403;
  - два запроса в пределах одного часа дают одинаковый `url` (округление `exp`);
  - `/internal/media-auth` снаружи (через Caddy) недоступен — проверить вручную после деплоя.
- После деплоя вручную:
  - прямая ссылка на `/media/original/...` без подписи даёт 403;
  - `/media/thumb/...` отдаётся;
  - у ответа с оригиналом нет `cf-cache-status: HIT`.

Сообщение для коммита: `feat(api)!: sign original urls and hide locked ones from guests`, футер
`BREAKING CHANGE: originals are served only via signed expiring urls; Photo.url is null for guests on locked photos, check Photo.locked.`
`url` становится nullable, а старые прямые ссылки на оригиналы перестают работать; отсюда `!`.

## Порядок выкатки

1. Фронт выкатывается **первым**: он уже переживает `url: null` и сам читает `locked` (см. ниже). Со старым API
   работает как сейчас.
2. Затем бэкенд, вместе с новым `Caddyfile`, `MEDIA_SIGNING_KEY` в `.env` и правилом Cloudflare «Bypass cache»
   для `/media/original/*`. Все три изменения выкатываются **одновременно** с кодом. Если выкатить только Caddy,
   все оригиналы начнут отдавать 403; если только код — подписи будут, но проверять их будет некому.

## Фронт (для справки, делается в репозитории фронта)

- `Photo.url: string | null`, `Photo.locked?: boolean`. Закрытость: `locked`, если поле пришло; иначе текущее
  правило на фронте (фолбэк до выкатки бэка, потом удаляется).
- Закрытые фото: размытое превью, клик ведёт на вход. В лайтбоксе закрытый слайд показывает размытое превью и ссылку на вход.
- Страница фото: закрыта, только если `locked`. Первые 10 фото галереи у гостя откроются и на своей странице.
- SSR всегда анонимный, поэтому после входа фронт перезапрашивает данные с токеном (первую страницу списка
  он уже перезапрашивает; добавится перезапрос `GET /photos/{id}`).
- `og:image` везде берётся из `thumbUrl`: у закрытых фото `url` нет, а у открытых он истекает.
- Подписанная ссылка истекла, пока страница была открыта: лайтбокс получает 403 на оригинал. Тогда фронт
  перезапрашивает фото и подставляет свежий `url`.
